# Observability: evaluations and open points

What was considered or rejected, what must be verified before it is relied on, and what is still pending. The resulting architecture is in [README.md](README.md).

## victoria-metrics-k8s-stack or separate releases

Decided on 2026-11-02: **`victoria-metrics-k8s-stack`**, one release, the components not needed disabled, [Grafana apart](#grafana-apart-from-the-stack). Compared with the chart (version 0.97, `values.yaml` and templates read on 2026-11-02).

| | `victoria-metrics-k8s-stack` (chosen) | Separate releases |
| --- | --- | --- |
| Releases to follow, besides Vector | Two: the stack (operator, kube-state-metrics, node-exporter are subcharts) and Grafana | Five: the operator, kube-state-metrics, node-exporter, Grafana, `kube-prometheus-stack` as a content package for its rules and dashboards |
| Scrapes of the control plane | From the chart, with the `job` labels the rules expect | Written by hand, the `job` labels kept in sync with the rules |
| Rules of the stack itself (`vmagent`, `VMSingle`, VictoriaLogs, `vmalert`, operator, Alertmanager) | Included | A `VMRule` to write |
| Data sources of Grafana | ConfigMaps generated by the chart | Written by hand |
| Rules and dashboards | Downloaded by a Job at each install or upgrade, from the upstream branches (see below), not followed by Renovate | Rendered by Helm from a pinned chart |
| Version of the chart | 0.x, with breaking changes between minors | `kube-prometheus-stack` is mature, the others too |

Why the stack: fewer moving parts to follow, and a set that VictoriaMetrics keeps consistent (labels, rules, dashboards). The price, accepted:

- **The Job of the rules and dashboards** (`syncJob`): a Helm hook `post-install,post-upgrade` that downloads the sources and creates the `VMRule`s and the ConfigMaps of the dashboards outside Helm and Flux. They are not restored if deleted by hand until the next upgrade, and an upgrade fails (then rolls back) if the sources cannot be downloaded. Its sources are the `main` or `master` branches of the upstream projects, [kept as they are](#sources-of-the-rules-and-dashboards).
- **A chart in 0.x**: read the changelog before each upgrade, no automerge.
- **One release for the metrics, the logs and the alerting**: a failed upgrade rolls back all of it. The CRs of the operator are only rolled back to their previous spec, which is harmless.

## Sources of the rules and dashboards

Decided on 2026-11-02: the `url`s of `defaultRules.sources` and `defaultDashboards.sources` keep their defaults, the `main` or `master` branches upstream. The Job only runs when the chart or the values change, so the content only changes with an upgrade of the chart, which is reviewed by hand anyway (no automerge).

| Option | Why not |
| --- | --- |
| Pinned to tags or commits, bumped by hand | Several URLs to compare with the defaults of the chart at each upgrade, and they lag behind what the chart expects (labels, recording rules of the dashboards). |
| Pinned, with a custom Renovate manager | A regex manager per source, and not every source has clean tags. |

The price: two installs a week apart may get different rules, and a rule may change without a commit. The noise pass covers it. To revisit if an upgrade brings a change that hurts: pin the source involved.

## Grafana apart from the stack

Decided on 2026-11-02: Grafana is its own release (`observability/grafana`), the subchart of the stack disabled. Not mandatory, preferred for:

- **The life cycle:** an upgrade of the stack does not restart Grafana, an upgrade of Grafana (a plugin that fails to download, a broken OIDC setting) does not roll back the metrics and the alerting.
- **Readability:** the OIDC block, the route, the ExternalSecret and the dashboards of the repository stay in their own folder.
- **The `volsync` component:** it needs `postBuild.substitute` on the Kustomization. Inside the stack, the substitution would also run over its values; the `kustomize.toolkit.fluxcd.io/substitute: disabled` annotation on the HelmRelease would avoid it, but apart the question does not arise.

The price: one more chart to follow, and the wiring between both (labels of the sidecars, URLs of the data sources) checked on the render rather than given by the chart.

## Vector or vlagent

Decided: **Vector for all the logs**. `vlagent` (the collector of the VictoriaMetrics family, a `VLAgent` resource in the operator) was compared on 2026-11-01 with the documentation.

| Need | vlagent | Vector |
| --- | --- | --- |
| Pod logs, as a DaemonSet | Yes, with Pod, Namespace and Node labels | Yes (`kubernetes_logs`) |
| Hubble files (`events*.log`, JSON) | Yes (`-fileCollector.glob`, checkpoints) | Yes (`file` source) |
| Talos: raw TCP or UDP `json_lines` | Not documented: it takes HTTP-based protocols | Yes (`socket` source), the one the Sidero and VictoriaLogs documentation use |
| Device syslog | The `-syslog.listenAddr.*` flags exist, the feature text does not mention it | Yes (`syslog` source: TCP, UDP, TLS) |
| Filter and transform (VRL), tags per device | Limited | Yes |
| Disk buffer, delivery to two VictoriaLogs | Yes | Yes (disk buffer per sink, one sink per target) |
| Managed by the VM operator | Yes | No: a Helm chart |

Why Vector: Talos cannot be received by `vlagent` as far as the documentation says, so Vector is needed anyway, and two collectors for the same job are worse than one. The price is a chart outside the stack and VRL to learn, the configuration being in Git.

Vector runs as two releases of the same chart: the agent (role `Agent`, DaemonSet) and the aggregator (role `Aggregator`, StatefulSet, two replicas). A single DaemonSet receiving the syslog too was not kept: the receivers would move with the nodes, and the LoadBalancer Service would spread the devices over every node. The Talos logs moved from the aggregator to the agent (2026-11-09): they come from the node itself, and the agent knows its node ([Talos destinations](#to-verify)).

## Memory of Vector

At the first deployment (2026-11-03), the agents were OOM killed about a minute after each start, at the 256 Mi limit: `anon-rss` of 254 MB in `dmesg`, a working set up to 571 MB with a 1 Gi limit. The peak only shows during a catch-up (the history of the pod logs, a disk buffer to read again); an agent up to date stays at 40 to 65 MB. After the peak, the allocator keeps the memory and gives it back slowly.

Measured locally with Vector 0.61.0: a `file` source reading 300k JSON lines (318 MB), a `remap`, the `elasticsearch` sink with a 512 MiB disk buffer, towards a fake `_bulk` answering in 50 ms. Peak RSS, two runs each:

| Variant | Peak RSS | Time to send |
| --- | --- | --- |
| Default (batches of 10 MiB) | 629 to 644 MiB | 3 to 4 s |
| `batch.max_events: 1000` | 378 to 397 MiB | 5 s |
| `batch.max_bytes: 1048576` (kept) | 322 to 340 MiB | 7 s |
| `batch.max_bytes: 524288` | 273 to 302 MiB | 10 s |
| 1 MiB and `request.concurrency: 2` | 270 to 279 MiB | 25 s |
| A `blackhole` sink, memory buffer / disk buffer | 136 / 240 MiB | |
| Drain of a full disk buffer only (the aggregator), default / 1 MiB | 495 / 264 MiB | 4 / 7 s |

The disk buffer itself costs about 100 MiB during a catch-up, the batches the rest: 1 MiB comes close to that floor, smaller batches or a fixed concurrency slow the catch-up for little. About 40k events per second at 1 MiB, against 1 to 3 per second per node in normal use. Hence 1 MiB batches on every sink, and a 512 Mi limit for the agent and the aggregator at first.

The bench has one source and one sink. On 2026-11-06, a network outage (the change of the GUA prefix of the nodes) cut the DNS and the API server for the pods; when they came back, the agent of kube-01 drained the disk buffers of both sinks, relisted the pods (`410 too old resource version`) and picked up the new log files, all at once (the API server alone had written about 390k lines in 20 minutes). It was OOM killed at 512 Mi (`anon-rss` of 503 MB in `dmesg`) a few seconds later, while the node had about 8 GiB available; the scrapes missed the peak (228 MB at most in the metrics). Hence a 1 Gi limit for the agent, the request unchanged (128 Mi). The aggregator stays at 512 Mi: one source of each kind, a peak of 57 MB so far.

## Rejected and alternative options

From general knowledge and the documentation, not tested here.

| Option | Why not |
| --- | --- |
| Prometheus (`kube-prometheus-stack` as the stack) | No highly available storage without a long-term layer (Thanos, Mimir), which means S3 and more components. VictoriaMetrics gets the level-1 HA with a replicated volume. |
| Separate releases | See [above](#victoria-metrics-k8s-stack-or-separate-releases). |
| Loki | A good fit with S3 storage, which is not wanted here. VictoriaLogs runs on a volume, and queries from Grafana through a plugin. |
| VictoriaMetrics or VictoriaLogs cluster mode | More components for a single user. The maturity of the VictoriaLogs cluster was not checked. Single node on a replicated volume is enough for level 1. |
| `vlagent` | See [above](#vector-or-vlagent). |
| Grafana Alloy, Fluent Bit | Not compared in detail: Vector covers the need. |
| Pushover provider of Flux | It does not exist: the supported types include `alertmanager`, `generic`, `telegram`, `matrix`, `discord`. Flux goes through Alertmanager. |
| Flux events to the Alertmanager | Used from stage 1 to stage 4: a `Provider` of type `alertmanager` and an `Alert` per namespace (an `Alert` only sees its own namespace), the events of the failed reconciliations. Replaced on 2026-11-12 by rules on `flux_resource_info` of the flux-operator ([alerting](README.md#alerting)). The events reach one Alertmanager replica only through the Service (the replicas do not share the alerts), so a `Provider` and an `Alert` per replica and per namespace, tied to `replicaCount`; they carry no end time (resolved by `resolve_timeout`, 1 hour), notify transient failures at once, and are a case apart in the template (their `message`, no `generatorURL`). What they had more: the full error message (now read from kube-state-metrics, [alerting](README.md#alerting)), and no delay. |
| `vmui` | Not wanted: Grafana is the only interface. |
| Alertmanager from a chart | `VMAlertmanager` comes with the stack, its configuration in the values. |
| Two `VMAgent` resources | One `VMAgent` with two replicas: without `shardCount`, each replica scrapes every target. |
| The receiver names in k8s-gateway | It only serves `shelltopia.org` (the user-facing names), from the routes. The receivers are infrastructure: `shelltopia.net`, host overrides in Unbound. An external-dns webhook for OPNsense/Unbound could publish them from the Services later ([open points](#open-points)). |
| Quiet hours in Alertmanager | The do-not-disturb mode of the phone (Android) already covers the nights. |
| A Grafana admin account for the reload of the sidecars | Only to let the sidecars call the reload API: a local password (or a service account token with server admin rights) to store and rotate, for data sources that change at an upgrade of the stack. Reloader restarts Grafana instead ([README](README.md#grafana)). |
| Cilium dashboards from grafana.com (16611, 16612, 16613) | Published for Cilium 1.12. The dashboards of the Cilium chart follow its version; the bootstrap creates `observability` before Cilium for them ([README](README.md#the-release-of-the-stack)). |
| Graphite for the NAS metrics | The *Reporting* exporter of TrueNAS 25.10 (`reporting.exporters`, `GRAPHITE` only) pushes to an IP (`destination_ip`, not a name): a Graphite listener on `VMAgent`, a LoadBalancer Service and pinned addresses (`192.168.19.3`, `fd38:4c4d:8f66:13::3`, freed), series named after the netdata charts of the NAS, and its community dashboard (20439) out of date, so to vendor and maintain here. Rejected for `node_exporter` (2026-11-12), deferred to the NAS platform work ([README](README.md#external-devices)). |
| The TrueNAS API exporter (dashboard 25081) | Rich (datasets, services, apps), but a third-party exporter tied to the middleware API, and an API key of the NAS stored in the cluster. The datasets and services are not what is needed; the ARC, the disks and the filesystems are, and `node_exporter` has them (its ZFS collector), with maintained dashboards (1860). |
| Dashboard 13659 for the HTTP checks | Its only revision (2020) selects by `job` and `instance`: `instance` is the URL, shared by the two modules of a URL, so the families cannot be told apart. Its panels are Angular `graph` panels. 14928 (revision 6) selects by `target`, one per URL and module, with current panels ([README](README.md#external-devices)). |
| `snmp_exporter` for the MikroTik devices | A module to generate from the MikroTik MIB, an SNMPv3 user per device. MKTXP reads the RouterOS API (`api-ssl`, verified TLS): switch ports, routerboard health, certificates, and the LTE of the KNOT (`gw-01`), maintained, with a dashboard (13679). SNMP stays for the Grandstream access point only; the SNMP user of `sw-01` and its item removed. |
| The chart of `nut_exporter` | DRuggeri ships one (`charts/nut-exporter`, a Helm repository on GitHub Pages, not OCI), checked 2026-11-12: `1.0.1` with `appVersion` `3.2.6`, behind the exporter (`v3.3.0`), so not released with it; its `ServiceMonitor` hard-codes `interval: 15s` and has no `params` (no `ups=eaton-ellipse`); `envSecret` puts the password in the values by default, an empty `securityContext`, no `affinity`; its rules are wrong (`UPSLowBattery` tests `LB == 0`). `app-template` instead. |
| Credentials for `nut_exporter` | Reading the variables of a UPS needs no login in NUT (`upsc` reads anonymously; the login serves `upsmon` and the instant commands), and `nut_exporter` only authenticates when given a username. No `ExternalSecret`; the item `nas-01-nut-server` stays in the `infrastructure` vault, for `upsmon` on the nodes (the store of the cluster only reads `kubernetes`). |
| Heartbeats for the silent hosts | A periodic message from each device proves it can send, at the cost of a scheduled job on every device (not all of them can). Thresholds per host on a counter of the aggregator (`syslog_events_total`) need nothing on the devices ([README](README.md#external-devices)). |
| Plain manifests for the chartless applications | See [below](#app-template-or-plain-manifests). |
| An OTLP receiver | Nothing pushes OTLP from outside the cluster: the metrics are pulled, the logs go through syslog, there is no traces backend. If a need appears: the `opentelemetry` source of Vector on the existing aggregator, or a new pinned address then. |
| TCP for the MikroTik syslog | Over TCP and TLS, RouterOS ends only the CEF entries with a delimiter (`cef-event-delimiter`); the `syslog` and `default` ones follow each other in the stream without one, and no option adds it (RouterOS manual, *Log*, 7.26). Seen on `sw-01` (2026-11-12): Vector received the entries merged into one, at the close of the connection. TCP with CEF would keep 1000 entries in memory during an outage and give fields (user, addresses, outcome), but CEF has no syslog priority: a `socket` source on a port of its own, `parse_cef` in VRL, one more port on the Service and in OPNsense, for one kind of device. UDP with `syslog` instead (2026-11-12), the entries lost while the aggregator is unreachable accepted for a switch ([README](README.md#external-devices)). |

### `app-template` or plain manifests

For `nut_exporter`, MKTXP and `opnsense-exporter`, which have no usable chart, and as the pattern of the [migration](../roadmap.md#migration) (most applications of `home` and of the Hetzner VM have no official chart). `app-template` kept (2026-11-12, [conventions](../conventions.md#charts)).

| | Plain manifests (`network/cloudflare-ddns`) | `app-template` of bjw-s (`oci://ghcr.io/bjw-s-labs/helm/app-template`, 5.3.0) |
| --- | --- | --- |
| What is written | `Deployment`, `Service`, `ServiceMonitor`, `ConfigMap`: about 120 lines for MKTXP | One `HelmRelease` and about 50 lines of values: controllers, containers, service, `serviceMonitor` (free `endpoints`, so `params` work), `configMaps`, `persistence` |
| Repository pattern | `OCIRepository` and `HelmRelease` for every other app; manifests for one temporary app | The same `OCIRepository` and `HelmRelease` pattern, remediation and rollback included |
| Readability | What you read is what runs | An abstraction: reading the values needs its schema, a render (`flux build`, `helm template`) to see the objects |
| Restart on config change | The Reloader annotation | Built-in (checksum of the ConfigMaps of the chart), or Reloader |
| Validation | `kubeconform` at best | A JSON schema of the values, errors at render |
| Renovate | The `kubernetes` manager, already configured | The chart through the `flux` manager; the image in the values needs the `helm-values` manager on `kubernetes/` |
| Upgrades | None besides the image | Majors with breaking changes (4 to 5 recently): every app migrated at once |
| Dependency | None | A popular chart (the standard of the home-operations community), mostly one maintainer |

### S3 storage

Not needed: the data lives on `replicated` volumes, the backup (if any) goes to B2. If a service is ever wanted, Garage is the suggested fit (lighter than MinIO, whose open-source maintenance status was not verified). SeaweedFS and RustFS were not evaluated.

## Open points

| Topic | Notes |
| --- | --- |
| Sizes and retention | Decided ([README](README.md#storage-and-retention)). Check the growth in the dashboards after two weeks, then expand the volumes if needed. |
| Noise of the alerts | A tuning pass after two weeks: rules disabled or their thresholds changed in the values, `warning` alerts that should be `info`. |
| Overcommit rules | `KubeCPUOvercommit` and `KubeMemoryOvercommit` disabled until kube-02 joins, then enabled again. |
| Flux objects stuck in `Unknown` | `FluxResourceNotReady` only matches `ready="False"`. An object whose reconciliation never ends stays `ready="Unknown"` without an alert. Usually Flux turns it `False` at the timeout of the reconciliation (the `timeout` of a Kustomization with `wait` or health checks, of a HelmRelease), and the alert follows. A stopped controller leaves its objects in their last state, but the default rules already watch its Deployment. At the noise pass: a rule on `ready="Unknown"` with a long `for` (an hour?), if a stuck object was missed. |
| `RecordingRulesNoData` on the scheduler | The three quantile rules of `kube-scheduler.rules` return nothing while no pod is scheduled: the histograms exist, but their `rate()` is 0, so `histogram_quantile` has no sample. On an idle cluster, the `info` alert goes `pending`, then `firing` after 30 minutes. Seen on 2026-11-12. Its `pending` state already makes `InfoInhibitor` fire in `observability`, as the upstream expression does not filter on `alertstate`: harmless, as that alert goes to `"null"`. At the noise pass: leave it as `info`, or disable `RecordingRulesNoData`, or exclude the scheduler group from it. |
| Receiver names | Static host overrides in Unbound for now. An external-dns webhook for OPNsense/Unbound could publish them from the Services; to look at later. |
| Syslog over TLS | Not for now (2026-11-12): the path from the devices crosses only devices of the network, server authentication does not stop forged logs (only mutual TLS would, a client certificate per device renewed by hand), and a refused chain silently drops the logs. To revisit if logs ever cross a network not under control. The design then: port 6514 on the aggregator, a cert-manager certificate (Let's Encrypt, DNS-01) for `syslog.kube-cluster01.shelltopia.net`, Vector restarted by Reloader at the renewal; TrueNAS, RouterOS and OPNsense support TLS, the access point was not checked. Talos cannot send over TLS: its logs stay on plain TCP, on the loopback of each node. |
| Rights of the OPNsense API user | OPNsense has no read-only API: the privileges of `opnsense-exporter` also allow editing the gateways and the WireGuard tunnels, and starting or stopping the services ([README](README.md#external-devices)). A leak of the key (a Secret of `observability`) gives them. The pass on the metrics (stage 5) drops the collectors not needed with their privilege; a collector whose rights are too broad for what it shows goes too. |
| Cardinality of `host` | `host` comes from the senders: anything reaching port 514 creates a stream and a series of `syslog_events_total`. Vector exports a series not updated for `flush_period_secs` (60 s) no longer: a silent host disappears from the counter, so `SyslogHostSilent` reads the past 7 days. At the alert pass: a cap, or an allow list of hosts, if it grows. |
| Volume of the firewall logs | Every filterlog line is kept. Measured over a week from stage 5e (`_time:1d host:fw-01 \| stats count(), sum_len(_msg)`), then `VLSingle` resized (30 Gi, 25 GiB cap, 30 days today). |
| NAS metrics | Deferred to the NAS platform work of the [Backups](../roadmap.md#backups) item: `node_exporter` and `smartctl_exporter` ([README](README.md#external-devices)). |
| `gw-01` | The MikroTik KNOT of the [LTE backup](../network/lte-backup.md): MKTXP and syslog as `sw-01`, item `gw-01-mktxp`, with that project. |
| Backup of the metrics | `vmbackup` to B2 or none ([backups](../backups/evaluations.md#open-points)). Probably none for the logs. |
| Hubble UI | Optional, after the metrics ([roadmap](../roadmap.md#security)). |
| Hubble flow metrics | To decide, with Hubble UI. The Hubble dashboards of the Cilium chart mostly read metrics that are not enabled (`flows_processed`, `tcp`, `icmp`, `port-distribution`, `dns`, `http`): only their `drop` panels can show data. **A:** enable `flow`, `tcp`, `icmp` and `port-distribution` with `labelsContext=source_namespace,destination_namespace` (the filters of *Network Overview (Namespace)*), low cardinality on this cluster; 90 days of history of the network traffic. **B:** keep `drop` and `policy` only, disable the Hubble dashboards of the chart (`hubble.metrics.dashboards.enabled: false`), and use Hubble UI for the live flows (only the last 4095 flows of each node); the history of the denied flows stays covered by the dashboard and the alert of the denied flows and by the Hubble export in VictoriaLogs. B is the lean option if Hubble UI is deployed. |
| HA tests | Lose a node holding `VMSingle` or `VLSingle`, once kube-02 joins: no gap in the data, Grafana back in a few minutes. |
| Flux cluster dashboard | The *Flux Cluster Stats* dashboard of the Flux monitoring example needs the Flux resources in kube-state-metrics (`customResourceState`). Only the control plane dashboard for now; the Flux failures reach Pushover through the alerts on `flux_resource_info` anyway. |
| Community dashboards still by `gnetId` | Vendored only *SNMP device* so far ([README](README.md#the-release-of-the-stack)). The others of the values to sort by publisher (the project itself, or an individual), those of individuals vendored the same way, their tables checked against the external labels of `VMAgent`. |
| Logs of Vector itself | The Vector pods carry `vector.dev/exclude: "true"` (default of the chart): their own logs never reach VictoriaLogs, only `kubectl logs` (and `--previous`) shows them. Their health comes from the metrics (errors, buffers, restarts, stage 4). To reconsider if a failure goes unnoticed. |
| ICMPv6 noise in the Hubble export | `DROPPED ... INVALID_SOURCE_IP ICMPv6 RouterSolicitation` from `fe80::` to `ff02::2`, on every node. Not filtered for now; drop it in `hubble_parsed` if it clutters the searches. |
| Flows to a pod that is gone | A connection to the IP of a deleted pod (a stale scrape target, a client still on the old address) has no identity left: Cilium sees `reserved:world-ipv4`, and the flow is audited, then dropped once the policies are enforced. Seen on 2026-11-12 after the `VLSingle` stop of the stage-4 tests: `vmagent` and the Vector agents to the old `vlsingle` pods, port 9428, two flows each, `NetworkPolicyAuditedFlows` (`info`) for an hour. `NetworkPolicyDroppedFlows` needs 10 minutes of drops: not reached by such flows. At the noise pass: nothing to do if it stays at restarts. |

Not watched for now; how to watch it is to find. |

The loss of one is partly seen by the default rules (`KubeDeploymentReplicasMismatch`, `TargetDown`). At the noise pass: a copy of `CoreDNSDown` per job, if that proves too blind. |
